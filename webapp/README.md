# Web Platform — Interactive Scouting Dashboard

---

The web platform is an interactive, unified scouting dashboard that translates the scientific findings, datasets, and mathematical formulations of the three completed hypotheses (H1, H2, and H3) and the similarity meta-study (H4) into actionable, visual tools for football scouts. 

By integrating **StatsBomb 360 spatial data** and **Transfermarkt market values** for UEFA Euro 2024, the dashboard provides scouts with a visual interface to look past ball volume and analyze players based on spatial value, decision-making, and style-based similarity.

---

## Actionable Scout Tools

The platform exposes four main capabilities, built around visual consistency and within-role benchmark comparisons:

### 1. Attribute Search & Filtering
Advanced filtering of the 272-player tournament pool. Scouts can isolate targets by:
* **Demographics**: Name search, age ranges, preferred foot, and team.
* **Economics**: Pre-Euro and post-Euro Transfermarkt market values.
* **Performance**: Threshold filtering on the four core indices (Progression, Dangerousness, Reception, Gravity, and Decision Quality).

### 2. Interactive Player Profiles
A unified view of a player's performance. The profile breaks down raw numbers into three specialized, role-benchmarked radar cards:
* **H1: Space Control & Value**: A 4-radar panel displaying Progression, Reception, and Gravity constructs along with the additive components of Dangerousness.
* **H2: Contextual Decision-Making**: A 4-axis radar measuring how well a player picks the best option, avoids the worst, and generates elite decisions compared to alternatives.
* **H3: Off-Ball Movement**: A 3-axis radar highlighting off-ball potential, average run quality (xEPV mean), and the latency indicating how often runs are left unserved.

### 3. Symmetric Head-to-Head Comparisons
Symmetric overlays of two players within the same macro-role. The interface overlays their H1, H2, and H3 radars directly on top of each other, aligning their within-role percentiles and calculating the Transfermarkt market value price delta to evaluate the trade-offs of budget vs. performance.

### 4. Stylistic Matchmaking (H4)
Given a target player, the system uses the 11-axis "style DNA" matrix to find the closest stylistic matches inside his own role, sorted by similarity score descending. This is the scouting question made concrete: *who plays like this expensive player, but costs less?*

## Component Architecture

The webapp is split into three core modules: data cleaning/import, backend server, and frontend client.

```
webapp/
├── data/                           # Data cleaning, database schema, and SQL importers
│   ├── data_raw/                   # Raw input CSV datasets from H1, H2, H3
│   ├── data_clean/                 # Relational clean targets generated by cleaner
│   ├── space_control_value/        # H1 datasets, bridge mapper, and H1 database script
│   │   ├── build_mapping.py        # Maps StatsBomb 360 names to Transfermarkt profiles
│   │   └── import_space_control.py # Imports H1 spatial metrics and Convex Hulls
│   ├── decision_quality/           # H2 datasets and H2 database script
│   │   └── import_decision_quality.py # Imports H2 decision accuracy and percentiles
│   ├── data_cleaner.py             # Parses and cleans raw datasets into clean targets
│   └── supabase_importer.py        # Re-creates core relational schema and maps baseline tables
│
├── backend/                        # FastAPI server exposing REST APIs
│   ├── database.py                 # SQLAlchemy database configuration and engine pool
│   ├── main.py                     # API controller, query engines, and similarity scoring
│   ├── import_off_ball.py          # Imports H3 URS off-ball movement metrics
│   ├── import_similarity.py        # Imports H4 player similarity metrics
│   └── requirements.txt            # Python backend dependencies
│
└── frontend/                       # React + TypeScript + Vite + Recharts client
    ├── src/pages/                  # Main routing views
    │   ├── Home.tsx                # Attribute search table and player catalog
    │   ├── SimilarPlayers.tsx      # Matchmaking, look-alikes list, and head-to-head overlays
    │   └── PlayerProfile.tsx       # Individual player cards detailing H1, H2, H3
    ├── src/components/             # Visual panels and modular charts
    │   ├── SpaceControlSection.tsx # Recharts implementation of H1's 4-radar block
    │   ├── DecisionQualitySection.tsx # Recharts implementation of H2's 4-axis radar
    │   └── OffBallSection.tsx      # Recharts implementation of H3's 3-axis radar
    └── src/index.css               # Core CSS design system token definitions
```

## Database & Data Pipeline

The backend reads data from a relational PostgreSQL database schema. Before running the servers, clean and import the datasets in the following order:

### 1. Generate Clean CSV Files
Process the raw output files from each hypothesis folder into structured tabular clean targets:
```bash
cd webapp/data
python data_cleaner.py
```

### 2. Import Core Relational Schema
Load the baseline tables (`teams`, `team_matches`, `player_totals`, `player_profiles`, `player_bridge`) into the database. Set your connection string via the `DATABASE_URL` environment variable or specify it with the `--db-url` flag:
```bash
python supabase_importer.py --replace
```

### 3. Build Name Mappings
Generate the name translation mapping that matches StatsBomb 360 player names to their corresponding Transfermarkt profiles (used for matching and profile loading):
```bash
python space_control_value/build_mapping.py
```

### 4. Import H1 Space Control Data
Import the Convex Hull spatial indices and aggregated performance data:
```bash
python space_control_value/import_space_control.py
```

### 5. Import H2 Decision Quality Data
Import the picks-the-best and worst-choice decision percentiles:
```bash
python decision_quality/import_decision_quality.py
```

### 6. Import H3 Off-Ball Data
Import the uncapitalized run scores (URS) and latency metrics:
```bash
python ../backend/import_off_ball.py
```

### 7. Import H4 Similarity Data
Import the within-role player similarity metrics:
```bash
python ../backend/import_similarity.py
```

## Developer Quick Start

To run the web app locally, start both the FastAPI backend server and the Vite frontend dev server.

### Backend Setup (FastAPI)
1. Navigate to the backend folder and activate your virtual environment:
   ```bash
   cd webapp/backend
   python -m venv .venv
   # On Windows:
   .venv\Scripts\activate
   # On macOS/Linux:
   source .venv/bin/activate
   ```
2. Install the Python dependencies:
   ```bash
   pip install -r requirements.txt
   ```
3. Configure your local environment by creating a `.env` file (copied from `.env.example`) and setting the `DATABASE_URL`:
   ```env
   DATABASE_URL="postgresql://user:pass@host:port/dbname"
   ```
4. Run the FastAPI development server:
   ```bash
   fastapi dev main.py
   ```
   The backend server will run on `http://127.0.0.1:8000`.

### Frontend Setup (Vite + React)
1. Navigate to the frontend folder:
   ```bash
   cd webapp/frontend
   ```
2. Install the Node modules:
   ```bash
   npm install
   ```
3. Launch the Vite local dev server:
   ```bash
   npm run dev
   ```
   The interactive platform will open on `http://localhost:5173`.

## Conventions & UI Specifications

* **CORS Policy**: Configured to natively accept requests from both `localhost` and `127.0.0.1` origins across ports `5173`/`5174` to prevent browser blockages during local execution.
* **Standardized Typography**: The entire UI uses the **Inter** font family (`font-display` and `font-sans`) for structural UI elements and labels, while reserving `font-mono` exclusively for numbers/metrics to ensure clean vertical alignment.
* **Radar Ticks Spacing**: Recharts radar tick labels utilize a custom placement offset (`offset = 34` in custom tick components) to push labels outward and prevent text overlap with the outer radar boundary lines.
* **Layout Stability**: Interactive toggle and comparison buttons are styled with fixed widths (e.g., `w-[110px]` for list compare selectors). This locks their container bounding boxes, eliminating layout shifting and stabilizing adjacent elements (like the similarity progress bar) when compare states are toggled.
* **Symmetric Compare Constraints**: Head-to-head pickers enforce same-macro-role selections. Radar overlays are only generated for players in the same role, ensuring that within-role percentiles are compared symmetrically.
* **Similarity Rescaling**: Similarity scores are calculated in the backend by loading the pre-calculated Euclidean distances from `player_similarity.csv` rescaled against the maximum possible distance `D = sqrt(11) * 100`.
